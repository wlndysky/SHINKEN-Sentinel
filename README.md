# 秦剑 / SHINKEN Sentinel：Windows 内核网络策略与生命周期安全研究框架

## 缘起

几年前，我曾经写下“基于恶意 IP 流量分析检测系统研究”这份大学生创新创业大赛项目计划书。那时的原始代码并不成熟，结构混乱，充满临时方案和无法落地的设想。它更像一段年轻时期留下的技术草稿，而不是一个真正可以长期维护的系统。

多年以后，这个项目重新回到我的视线里。借助新一代工具协作与反复审阅，我没有继续修补旧代码，而是从生命周期、并发模型和内核边界重新开始设计，让它从一份几乎无法维护的早期遗留，逐步变成一个有清晰责任边界的现代 Windows WFP 框架。

## 设计思路

Shinken Sentinel 不以堆叠规则为目标，而是试图回答一个更基础的问题：内核中的每一次网络决策，能否被解释、被约束，并在需要时安全地撤销？

因此，规则管理与网络分类被刻意分开。控制面只负责校验、版本和发布；数据面只读取不可变快照，在 WFP classify 热路径中完成匹配和裁决。新规则发布不会修改正在使用的快照，读者退出后旧快照才进入回收。

同样的原则也适用于生命周期。WFP 对象、流上下文、注入句柄、事件、线程和用户请求都有明确的所有者。停止时先关闭生产者，再注销回调、排空引用、等待线程退出，最后销毁对象；任何无法证明安全的清理步骤，都会阻止继续卸载，而不是伪装成成功。

这套设计不假设回调“很短”，也不假设卸载时“不会再进来”。内核回调可能在不同 IRQL、线程和时间到达，所以系统使用 rundown、引用计数、事件和显式状态转换建立可验证的会合点。用户态只通过版本化 IOCTL 进入，长度、版本、权限、溢出和状态转换都在内核边界重新验证。

新的模块边界围绕责任建立：`driver/` 负责入口，`runtime/` 负责生命周期，`wfp/` 负责平台对象，`rules/` 负责策略，`packet/` 负责数据路径，`control/` 负责控制协议。无法解释的早期行为被舍弃，而不是继续复制。

## 当前状态

当前仓库提供内核框架源码与构建工程，围绕 WFP 网络分类、不可变规则快照、IOCTL 控制和事件记录展开研究，不是完整的终端安全产品。

部分能力仍未接通：重定向、内容检查和数据包注入提交路径尚未实现；接口索引与用户 SID 条件仅保留协议标识，规则验证会拒绝使用这些条件。

当前实现采用以下资源与并发边界：

- WFP 管理对象由动态会话持有；确认关闭会话、撤下过滤器后，才排空流上下文并注销运行时 callout。BFE 正常停止/恢复期间保留运行时注册，重建会话内对象；清理结果无法确认时保留所有权，禁止带着存活回调卸载。
- 控制设备在所有子系统初始化、运行态激活后才发布。PERMIT 保留后续提供者的裁决权，不绕过其他防火墙；ALE 流上下文不再被当成注入标记。
- RATE_LIMIT 使用写路径分配的每规则令牌桶，未变更参数的规则跨快照共享状态；分配失败不发布新策略。排序使用原地堆排序；分类路径不再扫描固定 64 槽限流表，也不分配遥测事件节点。

### 研究限制

- 规则数量仍受协议上限 4096 条约束。限流按规则匹配事件计数，不是按数据包字节计速；修改 burst 时在构建新快照期间复制并截断桶状态，在途旧版本独立完成，不提供跨策略版本的全局原子计数切换。
- 流跟踪使用 1024 个哈希桶，每桶最多 256 条记录；桶满或分配失败仅放弃该流的跟踪，不改变已经计算的网络裁决。
- 遥测待消费队列最多 4096 条，满时丢弃新事件并计数；已消费环形缓冲区保留最近 1024 条。`FLUSH_EVENTS` 是非破坏性快照读取，重复调用可能返回同一事件，不是可靠消息消费协议。
- appId 匹配使用 ASCII-only FNV 哈希的路径归一化，存在哈希碰撞且不处理国际化、大小写之外的 Windows 路径语义，不能作为生产级 Windows 身份匹配依据。

### 权限模型与查询面

控制面采用 create-time handle-scoped capability 模型：特权判定在 `IRP_MJ_CREATE` 时于创建线程上下文执行一次，结果缓存到 KMDF file-object 上下文；后续 modify 命令检查该缓存标志。判定使用有效令牌：有模拟令牌时不回退到服务进程令牌，低模拟级别、受限令牌和 deny-only 管理员组不获修改能力。这避免了在专用 consumer 线程中每请求鉴权时错误地拿到 SYSTEM 令牌的问题。能力绑定在句柄对象上，因此 `DuplicateHandle` 或句柄继承会把 modify 能力传递给接收方，且创建后令牌组成员变化不会立即生效。SDDL 授予 Everyone 泛读权限，规则版本、枚举、统计、事件等查询命令使用 `FILE_ANY_ACCESS`，属于设计内的可观测性/诊断暴露面，不应被视为完整机密性边界。

## 模块

| 目录 | 职责 |
|---|---|
| `driver/` | DriverEntry/EvtDriverUnload + 控制设备/ACL |
| `runtime/` | 生命周期终态机、rundown、注入门、阻断原因历史 |
| `wfp/` | engine/provider/sublayer/callout/filter 安装与拆除状态机 |
| `rules/` | 规则快照存储、评估、匹配、RATE_LIMIT 令牌桶 |
| `packet/` | classify 热路径、流上下文和注入资源生命周期 |
| `control/` | IOCTL 协议与分发 |
| `telemetry/` | 静态有界事件队列、容量丢弃计数与最近事件快照 |
| `shim/` | 最小 WDK 垫片(仅 IR/宿主验证用) |

## 构建

- LLVM 路径：[build.bat](build.bat) 使用 `shim/` 进行语法检查、IR 生成与 `opt -O2` 优化，不生成可加载驱动。通过 `LLVM_DIR` 指定包含 `bin/clang.exe`、`bin/llvm-link.exe` 和 `bin/opt.exe` 的安装目录。
- WDK 路径：使用真实 WDK 头文件构建驱动，前置条件见 [WDK 构建说明](wdk/README_WDK.md)。在仓库根目录的 VS 开发者命令提示符中执行：

```bat
msbuild wdk\shinken_wfp.vcxproj /m /p:Configuration=Release /p:Platform=x64
```

## 验证边界

本发布仓库不包含测试套件、部署包或环境验证报告。编译与 IR 优化只能检查对应构建路径，不能证明内核并发安全或网络策略一定生效。源码中的裁决结果也不等同于系统最终执行结果；这里不作“全部通过真实内核验证”的声明。

GitHub Actions 的 [Source checks](.github/workflows/source-check.yml) 在 Windows runner 上复用 `build.bat` 的模块清单与 shim 参数，只运行 `clang -fsyntax-only`。它不运行 `build.bat`、WDK/MSBuild、链接、签名、安装或加载，也不生成对象文件、LLVM IR 或 `.sys`。通过仅代表 shim 路径可解析，不能证明真实 WDK API/ABI、内核并发或过滤行为正确。

## 名称

中文名称：**秦剑**。英文名称：**SHINKEN Sentinel**。

“秦剑”保留项目最初的中文来意；`SHINKEN` 并非“秦剑”的严格音译，而是借用了日语 `真剣`（しんけん）的另一层意味：真正的剑，也意味着认真、郑重。两个名字语源不同，却共同提醒这个项目：网络裁决、内核生命周期和每一次失败处理，都必须真实、准确，不能靠想象蒙混过去。

代码兼容名仍为 `SHINKEN WFP`，以保持现有服务、协议和内核对象身份的连续性。
